## 1. Цель и результат

Бот из ЛР1 расширен до AI-агента. Модель предлагает действие через нативный tool
calling, приложение проверяет его и выполняет через собственный MCP-сервер, а результат
использует для ответа. Функции ЛР1 (режимы, история, `/settings`, `/reset`) сохранены.

- Модель: ⟨`openai/gpt-4o-mini` через OpenRouter⟩, Chat Completions с `tools`,
  `tool_choice=auto`, `parallel_tool_calls=false`.
- MCP: официальный Python SDK `mcp==2.3.0`, протокол `2026-07-28`, транспорт stdio.
  Бот (MCP-хост) запускает сервер дочерним процессом; MCP-клиент — `app/mcp_gateway.py`.

## 2. Архитектура и роли MCP

- **Хост** — Telegram-приложение (`app/`): управляет моделью, историей, подтверждениями
  и подключением.
- **Клиент** — `McpGateway`: обнаруживает возможности и инструменты сервера, проверяет
  аргументы по `inputSchema`, вызывает инструменты и читает ресурс. Сессией владеет
  задача-супервизор, которая переподключается после разрыва.
- **Сервер** — `mcp_server/`: три инструмента и ресурс `schedule://current-week`.
  Каждый вызов сервер повторно валидирует сам.

Подробная схема — в README, раздел 12; контракты — в `spec.md`, раздел 2.

## 3. Инструменты и ресурс

| Инструмент | Тип | Вход | Выход |
| --- | --- | --- | --- |
| `get_weather` | чтение | `city` (1–100 символов) | `status`, `location`, `current` (°C, WMO-код и описание, ветер в м/с, время наблюдения и пояс), `candidates` |
| `get_schedule` | чтение | `date` (`YYYY-MM-DD`, реальная дата) | `lessons[] {start, end, title, location}`; пустой список означает «занятий нет» |
| `add_reminder` | изменение | `text` (1–500), `remind_at` (ISO 8601 со смещением, будущее) | `reminder_id`, нормализованное время, пояс, `created` |

Во всех `inputSchema` стоит `additionalProperties: false`. Схемы генерируются из
Pydantic-моделей с `extra="forbid"`. Высокоуровневый `MCPServer` из SDK молча
отбрасывал лишние аргументы, поэтому выбран низкоуровневый `Server` с явными схемами.

**Погодный сервис — Open-Meteo**: бесплатен, не требует ключа (нечего утечь), отдаёт
названия на русском (`language=ru`). Геокодер возвращает страну, регион и население,
что позволяет отличать одноимённые города. Правило неоднозначности: если вариантов
несколько и ни один не доминирует (≥ 100 тыс. жителей и ≥ 10× следующего), бот
перечисляет варианты и просит выбрать; первый результат автоматически не берётся.

**Расписание** — обезличенный файл `data/schedule.json` (4 недели). Путь задаёт только
конфигурация (`SCHEDULE_FILE`).

## 4. Агентный цикл и проверки

1. Модель получает историю, системную инструкцию режима с правилами работы с
   инструментами, текущее время и пояс пользователя, а также схемы из MCP-обнаружения
   и локальный `ask_clarification`.
2. Возможные решения: ответ, уточнение или вызов инструмента. Решение приходит в поле
   `tool_calls`, текст не разбирается.
3. Приложение проверяет имя по списку обнаруженных инструментов и аргументы по
   `inputSchema` (jsonschema): лишние поля, длины, формат даты. Для `add_reminder`
   дополнительно проверяется, что пояс задан, локальное время однозначно (переходы
   DST), смещение совпадает с поясом пользователя и время в будущем.
4. Чтение выполняется сразу. Результат проверяется по `outputSchema` клиентом SDK и
   передаётся модели как `role=tool` с пометкой источника и `untrusted_data`.
5. Не более 2 MCP-вызовов на сообщение: при попытке третьего обработка
   останавливается с сообщением, а в аудит записывается `limit`.

Ошибки MCP и внешних сервисов сводятся к единому `ToolCallError(code)`. Пользователь
получает короткий текст без стека и секретов. При сбое погоды бот отвечает
детерминированно, не давая модели придумать данные.

## 5. Подтверждение, часовой пояс и владелец напоминания

**Часовой пояс** хранится как имя IANA (`/timezone`) и проверяется по
`zoneinfo.available_timezones()`; на Windows базу даёт пакет `tzdata`. Модель не
выбирает пояс: без `/timezone` действие не готовится.

**Подтверждение**: состояния `pending → executing → done`, `pending → cancelled`,
`pending → expired`. Срок 5 минут, кнопки «Подтвердить» и «Отменить». Подтверждение
нельзя перенести на другого пользователя (все запросы фильтруются по `chat_id`) или на
изменённое действие (подпись привязана к хешу аргументов).

**Как сервер узнаёт владельца.** ⟨обоснование своими словами⟩ Бот при каждом запуске
генерирует случайный секрет и передаёт его только своему дочернему серверу через
переменную окружения. После подтверждения бот подписывает HMAC-SHA256 `chat_id` из
Telegram update, id действия, пояс, хеш аргументов и срок 1 минута, а затем передаёт
подпись в `_meta` запроса `tools/call`. Модель этих полей не видит. Сервер без секрета
(например, запущенный из MCP Inspector) отклоняет любой `add_reminder`, а посторонний
клиент не может подделать подпись. Альтернатива «передавать owner в аргументах» отклонена:
аргументы формирует модель.

**Идемпотентность**: `UNIQUE (chat_id, source_update_id)` в `pending_actions` защищает
от повторной доставки update. Атомарный `UPDATE … WHERE status='pending'` защищает от
двойного нажатия. `UNIQUE idempotency_key` (= id действия) в `reminders` делает повтор
после сбоя безопасным. Механизм проверен на PostgreSQL
(`test_concurrent_double_confirmation_creates_one_reminder`, `asyncio.gather` двух
подтверждений).

## 6. Команды `/tools`, `/why` и аудит

`/tools` строится из списка, полученного по MCP; если сервер недоступен, команда
сообщает об этом. `/why` берёт последнюю запись `agent_events` текущего пользователя:
время, действие, инструмент, безопасное резюме аргументов (без id, текст обрезан до 60
символов), статусы проверки и выполнения, число MCP-вызовов и причину. Причина берётся
из назначения инструмента, а не из текста модели, поэтому скрытые рассуждения и
промпт не попадают в ответ. В текстовом логе есть только случайный `request_id`,
действие, статусы и длительность — без Telegram ID и текстов.

## 9. Известные ограничения

- Уведомления о наступивших напоминаниях пока не отправляются (это задача ЛР3).
- Блокировка сообщений одного пользователя (`asyncio.Lock`) работает внутри одного
  процесса. Корректность подтверждения при этом обеспечивает БД, а не блокировка.
- Правило доминирования города эвристическое: для двух крупных одноимённых городов бот
  всегда спросит, а для «столица против деревни» выберет столицу.
- Если пользователь подтверждает действие в последние секунды перед `remind_at`, сервер
  отклонит прошедшее время. Бот честно сообщит об ошибке, а действие останется
  `pending` до истечения срока.
- Модель может не вызвать `ask_clarification` и ответить вопросом обычным текстом. Тогда
  в аудите это будет «ответ без инструмента», а в эксперименте — ошибка маршрутизации.

## 10. Использование AI-инструментов

⟨Проверить и дополнить своими словами.⟩ Для проектирования, генерации кода, тестов и
черновиков документации использовался Claude (Anthropic). Весь код проверен тестами,
сквозным прогоном через настоящий stdio-процесс MCP-сервера и мутационными проверками:
тесты должны падать, если отключить валидацию аргументов, лимит вызовов или
атомарность подтверждения.

Исправленные и отклонённые решения:

1. Сначала сервер был написан на высокоуровневом `MCPServer`. Пробный вызов показал, что
   лишний аргумент (`owner`) молча отбрасывается, а не отклоняется. Сервер переписан на
   низкоуровневом `Server` с Pydantic-схемами `extra="forbid"`.
2. Тестовая фикстура с `async with Client(...)` падала с ошибкой anyio «cancel scope in a
   different task»: pytest-asyncio выполняет вход и выход фикстуры в разных задачах.
   Тесты переделаны так, что клиент открывается внутри теста. Отсюда же решение держать
   соединение бота в отдельной задаче-супервизоре.
3. Первая версия тестов подтверждения проверяла только хранилище в памяти. Это не
   доказывает защиту от гонки, поэтому добавлен интеграционный тест на PostgreSQL. Его
   значимость проверена мутацией: при неатомарном захвате тест падает.
